## TL;DR

- Vibe Coding や Loop Engineering の恩恵を受けつつ、エンタープライズレベルで Claude Code を手放し運用するには、単純なコンテナ隔離だけでは足りない
- プロンプトインジェクションは「完全には防げない」を前提に設計する。防ぐのではなく、起きても漏れにくくする
- 三方向の多層防御を組む
    - 入口：Bedrock Guardrails によるプロンプトインジェクション検知
    - 出口：mitmproxy + 三段 DLP による外部通信監査
    - 鍵分離：Workspace に秘密を置かない設計
- AI エージェント自身が「知らない秘密」を漏らしようがない。LLM API キーは Bifrost が、ツール API キーは egress-proxy が肩代わりする

この記事では、実装した [HeartGarden](https://github.com/sniper-fly/HeartGarden) [^1] を題材に、各防御層の設計思想と実装を解説する。

[^1]: 由来はもちろん、某変身ヒロインアニメ。領域に閉じ込めて被害を及ぼさないようにする様子から。

---

## 1. はじめに: なぜ手放し運用に多層防御が要るのか

**Vibe Coding** や **Loop Engineering**[^2] といった言葉が示すように、AI コーディングの自律性はここ一年で急速に高まった。モデルの性能向上とハーネス技術の進展が重なり、タスクを渡せば人間がほぼ介入せずに完成まで走らせることが可能になってきている。

しかし開発速度が爆速化する一方で、AI が安全に、かつ利便性を犠牲にせず運用できる環境が整っていなければ、企業レベルの開発でこの恩恵を受けることはできない。そこで、既存コンテナサンドボックスの安全性・利便性の課題に本気で向き合った実装を考えてみることにした。

現状、速度・利便性と安全性はトレードオフになりがちだ。個人開発者は速度を取って相応のリスクを負い、エンタープライズの開発者は都度承認など安全側に倒すことで速度を失う。とはいえ AI をスピード感を持って活用することは生産性や成果に大きく寄与する。この非対称が複利で積み上がると、慎重な組織ほど競争力を失うリスクが生じる。HeartGarden は右上（両立）を狙う設計として提案する。

![安全性と速度・利便性のトレードオフ](/images/heartgarden-multilayer-sandbox/tradeoff.png)

[^2]: 「Loop Engineering」という用語の定義はコミュニティでまだ揺れている。

## 2. 使い方: 普段の `claude` をそのまま置き換える

仕組みの話に入る前に、利用イメージを先に示しておく。HeartGarden の Workspace コンテナの呼び出しは、普段の `claude` コマンドの代わりに薄いラッパーを挟むだけで済む。

リポジトリの `justfile` に Workspace 起動タスクが定義されており、`just claude` で呼び出せる。HeartGarden の `justfile` をどこからでも呼べるエイリアスとして `hg` を登録しておけば、`hg claude` でそのまま使える。

```bash
# シェル設定 (~/.zshrc など) に追記
alias hg='just --justfile <path/to/HeartGarden>/justfile --working-directory .'

# 以降はこれだけ
hg claude
```

`hg claude` を実行すると、Podman の Workspace コンテナ上で Claude Code が起動する。コンテナにバインドマウントされるのはコマンドを実行したカレントディレクトリだけで、その範囲の外側には FS 分離が成立する（詳細は 7.2）。

Claude Code 本体の履歴やセッション、ツールキャッシュなどは別途名前付きボリュームと専用のマウント点で永続化されるため、コンテナを再起動しても直前の作業状態のまま再開できる。普段使いの感覚は `claude` のままで、その背後でコンテナ隔離と本記事で述べた各防御層が働くという構成だ。

なお HeartGarden は Claude Code を動かすことに特化して実装しているが、設計自体はエージェント実装に依存しない。LLM API キーを外に追い出し、出口通信をプロキシで検査するという枠組みはそのまま、API 経由で動く他のコーディングエージェントにも同じ恩恵を持ち込める。

## 3. 既存の選択肢、それぞれの限界

Loop Engineering に既存のアプローチで応えようとすると、三択になる。

### 都度承認

最も安全側に倒した選択だ。コーディングエージェントがコマンド実行を行うたびに人間が確認する。事故は起きにくいが、ループが高速に回るほど人間がボトルネックになる。長時間の自律実行には成立しない。加えて、承認を繰り返すうちに確認が形骸化し「なんとなく Allow」という承認疲れが生まれるリスクもある。

### `--dangerously-skip-permissions`

すべての権限確認をスキップし、完全な手放し運用を実現できる。ただし、AI が何を実行するのかを把握しきれなくなる。ホストファイルの意図しない破壊、機密情報の外部送信、いずれも事後に気づく構造になる。

### Auto Mode

この二択の中間に位置する。Claude Code ではこの Auto Mode が存在し、ツール使用の許可・拒否を Claude 自身が自動判定することで、都度承認の摩擦を大幅に減らせる。

ただし判定ロジックの本体はプロンプトレイヤにある。プロンプトインジェクションで覆される可能性も否定はできない。Auto Mode 自体は実用的な選択肢だが、これを最後の砦にしてしまうと、プロンプトレイヤが破られた時点で防御が尽きる。プロンプトレイヤより下位の層でも多重に守る構造が必要になる。

## 4. 既存サンドボックス論の不足

「コンテナで囲めば安全」という議論見られるが、AI が自律的に動く環境では見落としがある。

### FS（ファイルシステム）分離だけではプロンプトインジェクション経由の漏洩を止められない

Docker や Podman でホストのファイルシステムから切り離しても、ネットワークは生きている。悪意あるコンテンツを踏んだ AI が「この API キーを外部サービスに送れ」という指示を受けたとき、FS 分離は無力だ。

### ホワイトリストだけでも漏れる

ドメインホワイトリストは有効な防御層だが、単独では穴がある。`github.com` は業務上ほぼ必須のためホワイトリスト入りする。しかしパブリックリポジトリに API キーを commit・push される経路は塞げない。「許可ドメイン経由の悪用」は構造的に発生しうる。

### 結論: プロンプトインジェクションがある前提で設計せよ

プロンプトインジェクションを 100% 防ぐことは難しい。この前提を受け入れるならば、プロンプトインジェクションをいかに防ぐかではなく、プロンプトインジェクションが起きたとしても安全にするにはどうすればいいかを考えることが重要になる。

## 5. 脅威モデル: 何を守り、何は守らないか

設計を語る前に守備範囲を明示する。

### 守る対象

| 脅威 | 説明 |
|---|---|
| AI によるホストファイルの破壊 | コンテナ外への副作用防止 |
| ホストの重要ファイルへの AI のアクセス | SSH 鍵・クラウド認証情報・ブラウザ Cookie 等 |
| AI による機密情報の外部送信 | プロンプトインジェクション経由も含む |
| API キーの流出 | LLM API キー・ツール API キー |
| 不正な外部接続 | ホワイトリスト外ドメインへの通信 |

### 守らない（前提から外す）もの

| ケース | 理由 |
|---|---|
| ホスト OS 自体が汚染されている | AI エージェント以前の問題 |
| Workspace を起動する人間が悪意を持つ場合 | 信頼の起点が崩れている |
| LLM プロバイダ自体の侵害 | サプライチェーンリスクは HeartGarden のスコープ外 |
| ホスト環境に機密情報が平文で保存されているケース | マウント経由で Workspace に漏れる可能性がある。HeartGarden は SSM から取得し FS に現れないよう設計するが、このスコープ外の秘密管理は利用者の責任 |
| ソースコード・設定ファイルに平文で秘密が書かれている場合 | AI 以前にアンチパターン。そもそも FS に秘密を持ち込まない設計（7.5）が前提 |

## 6. 「脅威 × 防御層」マトリックス

各脅威に対してどの防御層が何から守るのかを一覧にする。

| 脅威 \ 防御層 | コンテナ FS 分離 | 入口 Guardrails | 出口 DLP | 鍵分離 |
|---|:---:|:---:|:---:|:---:|
| ホストファイル破壊 | ◎ | − | − | − |
| ホスト重要ファイルへのアクセス | ◎ | − | − | − |
| 直接的なプロンプトインジェクション（危険指示） | − | ○ | △ | − |
| 言い換えによる機密漏洩誘導 | − | △ | ○（AI DLP） | ◎（鍵を知らない） |
| API キー流出 | − | − | △ | ◎ |
| 不正な外部接続 | − | − | ◎（ホワイトリスト） | − |

> 凡例: ◎ 主防御 / ○ 補助 / △ 部分的 / − 守らない

表を眺めると、機密漏洩系の脅威には複数の層が必要だ。特に「言い換えによる機密漏洩誘導」に対して ◎ を付けられるのが**鍵分離**だけである点に注目してほしい。AI が知らない秘密はどんな言い換えをしても漏れない、という構造的な保証だからだ。

## 7. HeartGarden の多層防御アーキテクチャ

### 7.1 全体像

HeartGarden は、Workspace コンテナから発せられる通信を **二系統のプロキシ** で捕捉する構造を取る。

![HeartGarden 多層防御アーキテクチャ](/images/heartgarden-multilayer-sandbox/architecture.png)

一系統目は **LLM 通信路**。Claude Code が LLM を呼ぶリクエストは `ANTHROPIC_BASE_URL` 経由で guardrails-proxy に届き、Bedrock Guardrails による入力検査を経て Bifrost（LLM Gateway）に転送される。Bifrost が API キーを保持するため、Workspace には LLM API キーが一切存在しない。

二系統目は **一般通信路**。git clone や npm install、ツール API の呼び出しなど、LLM 以外のすべての外部通信は `HTTP_PROXY` 経由で egress-proxy を通過する。ここでドメインホワイトリストと DLP 検査が行われる。

二つの経路は独立しており、内部 LLM 通信が誤って DLP にかかる事態を `NO_PROXY` 設定で回避している。

### 7.2 コンテナ FS 分離: AI に触らせない領域を作る

FS 分離はコンテナ型サンドボックスの基礎として語られることが多いが、担う役割は二つある。

- **事故防止**：AI が意図せずホスト側のファイルを削除・上書きする事故を物理的に防ぐ。Workspace 内で `rm -rf /` を実行しても、影響はコンテナ内に限定され、ホスト OS には届かない。
- **重要ファイルへの到達経路の遮断**：プロンプトインジェクションに成功した攻撃者が狙う典型的なターゲットは、LLM への API キーだけではない。SSH 鍵（`~/.ssh/`）、クラウド認証情報（`~/.aws/`、`~/.config/gcloud/` 等）、ブラウザの Cookie・セッショントークン、他プロジェクトのソースコードといったホスト側の高価値ファイルが主要な標的になる。Workspace から見えるマウント範囲を最小に設計することが、信頼境界そのものを意味する。

ただし FS 分離は「実行領域の隔離」であり、プロンプトインジェクション経由でネットワーク越しに情報を外部送信させる攻撃には効果がない。それを担うのが以降の層だ。

### 7.3 入口: Bedrock Guardrails でプロンプトインジェクション検知

guardrails-proxy は Workspace と Bifrost の間に立つリバースプロキシだ。Claude Code は通常通り LLM リクエストを送るだけで、すべてのリクエストが自動的に Bedrock Guardrails に通される。アプリケーション側の改修は一切不要である。

Guardrails は AWS のマネージドサービスとして、プロンプトインジェクション検知・有害コンテンツ検査・PII フィルタリングなどを提供する。

Guardrails も完全ではない。巧みに言い換えたプロンプトインジェクションは検知をすり抜けることがある。入口だけに頼らないことが、多層防御の大前提になっている。

### 7.4 出口: mitmproxy + DLP で外部通信を監査

egress-proxy は mitmproxy をベースとした TLS 中間者プロキシである。Workspace からの一般通信をすべて捕捉し、二段階の検査を行う。

第一段階はホワイトリストだ。許可されていないドメインへの接続は即座に遮断する。しかしホワイトリストだけでは足りない。GitHub や npm registry は業務上必須なためホワイトリスト入りしているが、それらの許可ドメイン経由でも API キーをパブリックリポジトリに push するなどの悪用は構造的に起こりうる。

第二段階は DLP（Data Loss Prevention）で、三段構成になっている。

1. **正規表現**：API キーやトークンの典型パターンを検出する
2. **Shannon エントロピー**：高エントロピーな文字列（規則性のある暗号的トークン）を検出する
3. **AI DLP**：上記を通過した通信に対し、自然言語に言い換えられた秘密情報の漏洩を LLM で検知する

AI DLP 自体も Bifrost 経由で内部 LLM を呼ぶ。DLP の処理が外部ネットワークに対して平文で漏れる経路は生じない。

### 7.5 鍵分離: 実行環境に秘密を置かない設計

知らない秘密は漏らしようがない。これが HeartGarden の設計思想の中心にある。Workspace（Claude Code が動くコンテナ）は、LLM API キーをいっさい保持しない。代わりに以下の二系統が認証を肩代わりする。

- **LLM API キー**：Bifrost が Virtual Key 認証で実キーを保持する。Workspace からは Virtual Key しか見えないが、Bifrost がプロバイダへのアクセスを仲介するため LLM は普通に使える
- **ツール API キー**：egress-proxy が肩代わりする。たとえば Web 検索ツールの API キーは Workspace 内に存在せず、egress-proxy が送信時に注入する

この設計において、プロンプトインジェクションで AI を操作して「API キーを教えろ」と命じても、AI はそもそも API キーを知らないため漏らしようがない。

鍵分離が守るのは「環境変数や設定ファイルに置かれた秘密」に限定される点は明示しておく。LLM の応答に含まれる社内コードの断片など、鍵以外の情報の流出は DLP（7.4）が担う。両者は守る対象が異なる独立した層であり、どちらかが欠けると防御に穴が生まれる。

なお API キーの長期保管には AWS SSM Parameter Store を利用しており、デプロイ時に `fetch-secrets.sh` が取得して podman secret に同期する。ファイルシステム上に秘密が現れる時間を最小化する設計だ。

### 7.6 永続的な開発環境: 名前付きボリューム + mise

セキュリティと利便性はトレードオフになりがちだが、使われないサンドボックスはセキュリティゼロに等しい。

コンテナの揮発性は実用上の最大の障壁だ。コンテナを再起動するたびにインストールしたツールが消えるのでは、開発環境として成立しない。HeartGarden では名前付きボリュームでツールキャッシュや依存を永続化し、mise（ツールバージョン管理）で再現可能なツール構成を維持している。PC を再起動しても、次回 `podman-compose up` で同じ状態のまま作業を再開できる。

### 7.7 信頼境界: Workspace は内部ネットワークのみ

Workspace コンテナは `bifrost-net` と `egress-net` という二つの内部専用ネットワークに属しており、直接インターネットへ出る経路を持たない。

Bifrost と egress-proxy は Workspace からのアクセスのみを受け付け、外部からの直接接続を許可していない。Workspace が信頼の起点であり、その外側にいる周辺プロキシが認証と検査を担う構造だ。ホスト OS 自体が汚染されているケースは、AI エージェント以前の問題であり脅威モデル（5 章）で「前提から外す」としている。

## 8. 現状の課題と限界

### DLP の検知漏れと残存リスク

巧妙に構成された自然言語による漏洩誘導は AI DLP でも見逃すことがある。多層防御の本質は「すべてを防ぐ」ことではなく「攻撃コストを跳ね上げる」ことなので、目的は達成できる。

### Guardrails / DLP の偽陽性問題

Guardrails によるプロンプトインジェクション検知や DLP は、正常な業務リクエストを誤検知（偽陽性）することがある。長めのコードスニペットや Base64 エンコードされた画像データが DLP に引っかかるケース、英数字が混在するランダム文字列が高エントロピー判定されるケースが実際に発生している。

### mitmproxy 証明書による既存ツールとの相性

egress-proxy は TLS 中間者プロキシであるため、独自の CA 証明書を Workspace に信頼させる必要がある。多くのツールはシステムの証明書ストアを参照するため問題は起きないが、一部のツールは独自の証明書ピン留めを実装しており、そのままでは接続が弾かれる。ツールを追加するたびに個別の設定確認が必要になるケースがあり、運用摩擦の一因となっている。

### 永続開発環境としての Podman の適性

Podman は本来、一時的なコンテナ実行に最適化されている。名前付きボリュームと mise でかなりの部分を解決しているが、永続的な開発環境としては VM や Incus コンテナのほうが柔軟性が高い可能性がある。

### LLM プロバイダのサブスクリプション課金には非対応

LLM 通信はすべて Bifrost を経由し、API キーによる認証で各プロバイダに接続する構造になっている。このため、Anthropic の Claude Pro / Max など、ブラウザログインを前提としたサブスクリプション課金には対応していない。料金は API 従量課金となる。サブスクリプションを使い切る運用や、API 課金を避けたい用途には向かない。

（OpenAI のサブスクリプションについては、プロキシ越しでも利用できる可能性があるという情報を見かけたが、筆者は未検証である。動作を保証するものではない。）

### Bifrost のメンテナンスコスト

Bifrost はバージョンアップの頻度が高く、ユーザー側のメンテナンスコストが発生する。Cloudflare AI Gateway のようなマネージドサービスへの移行も検討したが、現状では予算上限管理やフォールバック機能が要件に届かず見送っている。

## 9. まとめ

プロンプトインジェクションは完全には防げない。極力起こさないようにすべきだし、起きたとしても機密が守られるようにすべきである。

HeartGarden が出した答えは三方向の多層防御だ。

- **入口（Bedrock Guardrails）**：危険な指示をできるだけ早い段階でブロックする
- **出口（mitmproxy + 三段 DLP）**：ネットワーク経由の漏洩経路を見張る
- **鍵分離**：実行環境に秘密を置かないことで、漏らせる秘密そのものを消す

この三層は守る対象が異なり、相互補完の関係にある。完璧な防御ではないが、再現可能な設計として組み合わせることで攻撃コストを跳ね上げられる。

HeartGarden は銀の弾丸ではないが、安全な手放し運用を成立させる多層防御の現実解の一例として参考になれば幸いだ。

(なお、HeartGarden 自体の OSS 化に関してはまだまだハードルがあるが、需要があれば...)
