## TL;DR

## なぜ作ろうと思ったか

アニメ好きをいつも悩ませるのが、アニメが特定のストリーミングサイトで独占配信されることである。
そんな独占配信だが、TV放送はされることがあるので録画することで、いわばアニメのベンダーロックインを避けることができる。
したがってアニメ好きは、新しいアニメの放送が始まる前にどのアニメが独占配信であるのかの情報を仕入れるという行事を毎シーズン挟むことになる。
例えば、以下のサイトが活用できるが、情報が不完全であることが多い。

https://abemaquick.com/1-delivery-2026winter-anime/

アニメ系youtuberが手間暇かけて全公式サイトをたどり、どのアニメが独占配信なのか調べてくれるケースもあるが、その情報も不完全である場合がある。

今回、私のケースでは「メダリスト２期」が独占配信であることを知らずに１話を録画し損ね、悲嘆に暮れたものだ。
もうこの惨劇を繰り返すまいと、エンジニアの私はClaudeCodeの機能をフル活用して、独占配信録画し忘れを一匹残らず駆逐すると決意した。

## 立ちはだかる壁

基本戦略としては、新シーズンのアニメの公式サイトのリンク一覧を取得しそこに記載されている配信情報をスクレイピングすることである。

しかし、これを実行するには以下の壁を乗り越える必要がある。

- 公式サイト一覧を取得する壁
- 公式サイトから配信情報を取得する壁
- コンテキスト量の壁
- MCP並列実行の壁
- コマンド許可確認地獄の壁
- bot対策bypassの壁
- コストの壁

## 公式サイト一覧を取得する壁

そもそも、新シーズンに放送されるアニメの一覧を取得する必要がある。
愚直にやろうとすると、アニメイトの新シーズンのページをスクレイピングして一覧を出す、とかになりそうだが、そもそもスクレイピングは不安定なのでできれば避けたい。
実は、そこまで難しい手段をとる必要はなく、Anilist APIが公式サイトのリンク情報を提供してくれている。

## 公式サイトから配信情報を取得する壁

アニメの公式サイトは、配信情報の記載が実にバラバラである。
トップページに配信情報が書いてあったり、`<domain>/onair/index1.html` に書いてあったり、トップページにアクセスしたらモーダルが出てきたり...
さらに、配信情報が載ってはいるものの、個別課金、都度課金サイト、とか書いてあればそれは結局配信サイトでは無料で見れないとか、シーズンごとに配信サイトが違ったり、これを機械的にルールを与えてスクレイピングするのは超絶難易度が高い。
そこで、ClaudeCodeを使うことによりウェブサイトをPlaywright MCPを使いエージェンティックに探索し、スクレイピングすることで解決する。

## コンテキスト量の壁

しかし、1シーズンごとに放送されるアニメは40-50件あり、これをClaudeCodeの一つのコンテキストで順番に探索するのは不可能では無いが、時間もかかる上にコンテキストが増えすぎて動作が不安定になるのは目に見えている。
そこで、サブエージェントを使い、アニメの数だけそれを起動して直列ではなく並列で実行し、さらにコンテキストも分けるようにする。

## MCP並列実行の壁

サブエージェントを複数作り、Playwright MCPで並列探索しようと思ったが、MCPサーバーの制約上、同じコンテキスト（LLMのコンテキストではなく、Playwrightのコンテキスト）を共有することになり、マウスクリックとかページ移動などを同じウィンドウに対して操作してしまうため、並列探索に堪える仕様になっていない。

playwright-cliを使うことで、セッションを分けることができ、さらにmcpの面倒な権限許可設定とかも気にしなくて済むようになった。

## コマンド許可確認地獄の壁

ClaudeCodeでは基本的なコマンドはsettings.jsonで allow を書けば許可することができるが、
`&&` を含むようなマルチステップワンライナーなどの複雑なコマンド、`$()`でなにか展開しているコマンドは攻撃防止のためか
毎回確認を求めてくる。10並列で作業していると、どの作業でどうして確認を求められているのかわからないままとりあえずYesを押すために
画面に張り付いていなければならなくなる（もはや自分でサイトをクローリングしたほうが全然早い）

`--dangerously-skip-permissions`を使う以外にこれを回避する方法がない（厳密にはまだあるが）ので、仕方なくDockerで隔離されたsandbox環境を作ろうとするが、やはりホスト環境とは勝手が違うのでClaudeCodeのTUIがバグったりしてうまくいかない。

### アーキテクチャ

streaming-jinarashiプラグインは3つのスキルで構成される。

```
streaming-jinarashi/
├── skills/
│   ├── anime-official-site-researcher/  ← AniList APIでアニメ一覧を取得
│   │   ├── SKILL.md
│   │   └── scripts/fetch_seasonal_anime.py
│   ├── anime-streaming-researcher/      ← 公式サイトから配信情報を収集
│   │   ├── SKILL.md
│   │   └── references/streaming-services.md
│   └── dokusen-kuchiku/                 ← 上記2つをオーケストレーション
│       ├── SKILL.md
│       └── references/report-format.md
└── hooks/hooks.json                     ← セッション開始時にPlaywright CLIをインストール
```

**処理フロー:**

```
[dokusen-kuchiku（独占駆逐）]
    │
    ├─ Step 1: anime-official-site-researcher
    │   └─ AniList GraphQL API → シーズンの全アニメ + 公式サイトURL
    │
    ├─ Step 2: anime-streaming-researcher (最大10並列)
    │   └─ Playwright CLIで各公式サイトを巡回 → 配信サービス情報を抽出
    │
    └─ Step 3: 結果集約
        └─ 独占配信 / 複数サービス配信 / 未確認に分類 → サマリーレポート生成
```

## 壁1: 公式サイト一覧を取得する

そもそも、新シーズンに放送されるアニメの一覧を取得する必要がある。
愚直にやろうとすると、アニメイトの新シーズンのアニメ一覧ページをスクレイピングして一覧を出す、とかになりそうだが、そもそもスクレイピングは不安定なのでできれば避けたい。
実は、そこまで難しい手段をとる必要はなく、AniList APIが公式サイトのリンク情報を提供してくれている。

GraphQL APIで、シーズンとを指定すればアニメの公式サイトURLが取得できる。

```python
GRAPHQL_QUERY = """
query ($season: MediaSeason, $seasonYear: Int, $page: Int) {
  Page(page: $page, perPage: 50) {
    pageInfo { hasNextPage }
    media(season: $season, seasonYear: $seasonYear, type: ANIME, format: TV) {
      title { romaji native }
      externalLinks { url site type }
    }
  }
}
"""
```

## 壁2: 公式サイトから配信情報を取得する

アニメの公式サイトは、配信情報の記載が実にバラバラである。
トップページに配信情報が書いてあったり、`<domain>/onair/index1.html` に書いてあったり、トップページにアクセスしたらモーダルが出てきたり...
さらに、配信情報が載ってはいるものの、個別課金、都度課金サイト、とか書いてあればそれは結局配信サイトでは無料で見れないとか、シーズンごとに配信サイトが違ったり、これを機械的にルールを与えてスクレイピングするのは超絶難易度が高い。

そこで、Claude CodeとPlaywrightを使うことによりウェブサイトをエージェンティックに探索し、スクレイピングすることで解決する。これを `anime-streaming-researcher` スキルとしてSKILL.mdに定義した。

### SKILL.mdの設計: ハイライトとアクセシビリティ

配信情報のスクリーンショットに「どの情報を参考にしたか」を示すため、該当テキストの背景色を黄色でハイライトしてからスクリーンショットを撮る機能を追加した。

しかし、ここで2つの問題が発生した。

**問題1: 個別課金セクションまでハイライトされる**

ページ全体にキーワードマッチをかけると、参考にしていない「個別課金サービス」セクションのサービス名まで黄色くなってしまう。

最初はSKILL.mdにTreeWalker APIを使ったコード例を書いていたが、AIがそれをそのまま使ってしまいサイトごとのDOM構造の違いに対応できない。結論として、**コード例をあえて例示せず原則だけを記述する**方針にした:

```markdown
- ハイライト対象は実際に streaming_service の根拠として参照したセクション・要素のみに限定
- ページ全体へのキーワードマッチは避ける
- 探索ステップで取得した snapshot のDOM構造を活用し、根拠セクションのコンテナ内のみをハイライト
```

> **学び:** SKILL.mdに具体的なコード例を書くと、AIがそれをそのまま使う。サイトごとにDOM構造が異なるなら、コード例ではなく**判断基準（原則）**を書く方が柔軟に対応できる。

## 壁4: MCP並列実行の壁

サブエージェントを複数作り、Playwright MCPで並列探索しようと思ったが、MCPサーバーの制約上、同じコンテキスト（LLMのコンテキストではなく、Playwrightのコンテキスト）を共有することになり、マウスクリックとかページ移動などを同じウィンドウに対して操作してしまうため、並列探索に堪える仕様になっていない。
そこで、当初はMCPサーバーを10個起動し、Skillの引数にどのMCPサーバーと通信するか指定することで解決しようとした。
しかし、この方法には権限管理の煩雑さという別の問題もあった。`allowed_tools` に `mcp__plugin_streaming-jinarashi_playwright__browser_navigate` のような長大なツール名を列挙する必要があり、MCPサーバーを10個分設定するとなると可読性も低くて面倒なことこの上ない。

### Playwright MCP → Playwright CLI

playwright-cliを使うことで、セッションを分けることができ、さらにMCPの面倒な権限許可設定とかも気にしなくて済むようになった。

#### セッション名の自動生成による並列分離

10並列でブラウザを動かすため、セッション名の自動生成ルールを設計した:

```markdown
1. 英語（romaji）タイトルからアルファベット・数字・スペース以外の特殊記号を除去
2. スペースをハイフン `-` に置換
3. 小文字に変換

| 英語タイトル                             | セッション名                          |
| ---------------------------------------- | ------------------------------------- |
| Sousou no Frieren                        | sousou-no-frieren                     |
| Re:ZERO -Starting Life in Another World- | rezero-starting-life-in-another-world |
```

#### eval vs run-code の使い分け

CLIへの移行時に発覚した細かい問題として、ハイライト処理のコードが `eval` で動かないことがあった。`eval` は単一式の評価用で、関数定義や `forEach` を含む複数行コードはシリアライズエラーになる。代わりに `run-code` を使う必要がある:

```markdown
**注意:** ハイライト処理は関数定義やforEachを含む複数行コードになるため、
`eval` ではなく `run-code` を使用すること
```

#### SessionStart Hookによる自動セットアップ

Playwright CLIをセッション開始時に自動インストールするHookも追加した:

```json
{
  "hooks": {
    "SessionStart": [{
      "matcher": "startup",
      "hooks": [{
        "type": "command",
        "command": "npm install -g @playwright/cli@latest && playwright-cli install --skills"
      }]
    }]
  }
}
```

> **学び:** Playwright MCPは強力だが、権限管理やSub-agentとの連携で煩雑さが生じる。Playwright CLIなら `Bash` ツールさえ許可すれば動くため、プラグインのポータビリティが格段に高い。

## Claude Codeプラグイン開発で得た知見

### 1. 柔軟性を重視する場合はコード例より原則を書く

具体的なコード例をSKILL.mdに書くと、AIがそれをそのまま使ってしまう。サイトごとにDOM構造が異なるなら、コード例ではなく**判断基準（原則）**を書く方がAIが柔軟に対応できる場合がある

### 2. MCPよりCLIの方がシンプルなケースがある

Playwright MCPは強力だが、権限管理やSub-agentとの連携で煩雑さが生じる。Playwright CLIなら `Bash` ツールさえ許可すれば動くため、プラグインのポータビリティが高い。セッション分離（`-s=`）も並列実行に不可欠だった。

### 3. 「仮定で進めずAskUserQuestionで確認を求めること」プロンプト

SKILL.mdに「不明点はAskUserQuestionで確認」と書くだけで、AIが適切な判断ポイントを自分で見つけて質問してくる。プラグイン開発に限らず、あらゆる設計で使える。


## おわりに

既存のソフトウェア開発における調査、実装タスクなどはAIによって仕様書を書いたり、ガードレールをうまく設計することでかなりスピード感をもってアクセル全開で進めることができるようになった。
が、プラグイン開発はLLMの動作を扱うため不安定なものも多い上、ClaudeCodeの新しい機能を使って開発する際は情報も少なく、バグなのか仕様なのかよくわからない動作などもあり、ブレーキを踏みながら開発している感覚だった。

「動くものをつくる→テストする→問題を見つける→調査する→改善する」の反復プロセスを地道に行う必要があり、AI登場以前の昔ながらの開発体験にも似ており、これはこれで楽しかった。

  2026年2月22日~23日の約2日間、28以上のClaude Codeセッションを通じて反復的に開発。大きく5つのフェーズに分けられる。             

  ---
  Phase 1: 初期構築 (2/22 18:40~19:06)

  やったこと: skill-developmentスキルを使って anime-streaming-researcher と dokusen-kuchiku のSKILL.mdを初期作成。

  ハイライト: AskUserQuestionによるインタラクティブな要件定義
  - dokusen-kuchikuオーケストレーションスキル作成時、AIが3つの質問をユーザーに投げた:
    a. 「最終成果物は何？」→ 集約レポートを選択
    b. 「Playwright MCPの可用性チェック方法は？」→ mcp__playwright存在確認を選択
    c. 「レポート形式は？」→ Markdownを選択
  - 「仮定で進めず確認を求めること」という指示が効果的に機能した例

  ハイライト: 初回テストでゴミファイル問題が発覚
  - ゴールデンカムイ最終章を初テスト → 成功するも、探索段階で撮ったスクリーンショット (kamuy_toppage.png)
  がプロジェクトルートに残留
  - ユーザーが「アイデア壁打ちしたい」と持ちかけ、AIが2つのアプローチを提案:
    - 案A: 探索段階ではファイル生成しない（snapshot/evalのみ）
    - 案B: 中間ファイルもREPORT_OUTPUT_DIR配下に限定
  - 案Aをベースにフォールバック付きで採用 → SKILL.mdに「探索段階のファイル生成ルール」セクション追加

  ---
  Phase 2: UX改善の反復 (2/22 19:06~19:28)

  ハイライト: ハイライト機能の追加とアクセシビリティ問題
  - エビデンスのスクリーンショットに「どこを参照したか」を示すため、テキスト背景を黄色でハイライトするコード例（TreeWalker
  API使用）をSKILL.mdに追加
  - その後のテストで「元の文字色が白だとハイライト背景と被って読めない」問題が発覚
  - 解決策: ensureContrast()関数を追加。相対輝度を計算し、明るすぎるテキスト色を #333 に補正

  ハイライト: 個別課金サービスの誤ハイライト問題
  - ページ全体にキーワードマッチをかけると、「個別課金」セクションのサービス名まで黄色くなってしまう
  - ユーザーが「コード例をあえて例示せず、その場で考えさせるべき？」と質問
  - 解決策: ハイライト対象を「定額見放題セクションのコンテナ内のみ」に限定するルールを採用

  ハイライト: ブラウザクリーンアップの明示化
  - メモリリーク防止のため browser_close を必須化 → SKILL.mdに「ステップ3: ブラウザクリーンアップ」追加
  - 配置ミス（キーワード一覧セクションの下に置いてしまう）→ 即座に検出・修正

  ハイライト: 日本語ファイル名のパスエスケープ問題
  - Haikuモデルでの実行時、日本語タイトルのディレクトリパスにバックスラッシュ (ゴールデンカムイ\ 第三期) を入れてしまい ENOENT
  エラー
  - 自己回復: ディレクトリ存在確認→正しいパスでリトライ→成功

  ---
  Phase 3: アーキテクチャ課題の露呈 (2/23 12:09~13:29)

  ハイライト: Sub-agentのPlaywright MCP権限問題
  - dokusen-kuchikuからTaskツールでGeneral-purpose Sub-agentを起動 → Sub-agentがPlaywright MCPツールにアクセスできず失敗
  - 原因: SKILL.mdのallowed_toolsにPlaywright MCPのツール名が宣言されていなかった
  - 修正: mcp__plugin_streaming-jinarashi_playwright__browser_navigate 等5つのツール名を追加

  ハイライト: Sub-agentがSKILL指示に従わない問題
  - 権限問題を修正後も、Sub-agentがスクリーンショットやエビデンスハイライトを実行しない
  - ユーザーが「SubAgentがSkillの指示に従ってスクショとかしてないんだけどなにかエラー履いてない？」と調査を指示
  - Sub-agentのログを調査するも根本解決に至らず

  ハイライト: Task Sub-agentからSkillツール直接呼び出しへの変更
  - ユーザーが「step 2でgeneral-purpose agentを起動するのではなく、Skillツールで呼び出すのみに設定して」と指示
  - AIが一度順次実行に書き換えてしまう → ユーザーが「順番実行ではなく並行実行することに変わりはない」と訂正
  - 修正: 「全アニメに対してSkillツールの呼び出しを1つのメッセージ内で同時に行う」+ 最大10並列バッチ処理に修正

  ---
  Phase 4: Playwright MCP → Playwright CLI への大転換 (2/23 14:40)

  最大のハイライト: 技術スタック全面刷新

  ユーザーの一言:
  「playwright MCPではなくplaywright cliを使えば、こんな面倒なことせずに済みそう」

  - Playwright MCPの権限問題、ブラウザコンソールログの汚染、Sub-agentとの連携の煩雑さなど、累積した課題を一挙に解決する判断
  - 既存の .claude/skills/playwright-cli/SKILL.md を参照し、両スキルのSKILL.mdを全面書き換え
  - 新たに追加された設計:
    - セッション名生成ルール（romajiタイトルからハイフン区切りの小文字に変換）
    - -s={SESSION_NAME} による並列実行時のブラウザセッション分離
    - eval と run-code の使い分け（ハイライト処理は複数行コードのため run-code 必須）
    - playwright-cli -s={SESSION_NAME} close による確実なクリーンアップ

  Phase 5: Playwright CLIでのテストと安定化 (2/23 14:55~15:34)

  - オーケストレーションテスト（2026 WINTER 先頭3アニメ）→ 複数回実行して安定動作を確認
  - 最終成果物: 3アニメの配信調査レポート + サマリーレポート生成
